# 从 Agent Flow 到 AI Native：为什么通用 Agent 是饮鸩止渴

我最近一直在做一个小玩具：**Agent Flow**。

它最初只是想解决一个很具体的问题：有些长链路任务，单个 Agent 和一份 Skill 很难稳定跑完，但确定性的流程、业务接口、RPA 和几个能力不同的 Agent 可以一起完成。

![Agent Flow 把确定流程、业务接口和 Agent 节点组织成可回收链路](./assets/agent-flow-overview.png)

Flow 不负责假装智能。它只负责链路控制、任务下发、结果回收和失败处理。真正执行任务的是 Node：它可以是一个业务 Agent、Codex、RPA、API，也可以是一段毫不起眼的 hardcode。

这件事让我越来越确信：**通用 Agent 往往不是产品目标，而是对产品目标尚未想清楚时的替代品。**

## 用户要的是任务完成，不是 Agent 表演

很多用户的真实需求并不宏大。

他们可能只是想从三个系统取数据，合并成报告，写进文档，再发送到群里。这个任务有固定顺序、真实权限和明确结果，只有其中少数节点需要模型判断。

如果把整条链路交给一个通用 Agent，它需要在一次长 Loop 里不断探索工具、恢复状态、判断下一步。两次运行可能走出两条路径，一次成功，一次失败。为了补救，系统继续叠加 Memory、Planner、Reflection 和更多 Loop，最后用户承担等待、成本和不确定性。

但如果把链路拆成几个可验证节点，确定性的部分交给 Flow、YAML、API 和代码，需要语义判断的部分再交给模型，问题会简单很多。

用户不关心你用了 RAG、MCP、Multi-Agent 还是最新的框架。他只关心：**我的问题解决了吗？下次还能稳定解决吗？**

## 最小任务单元也是 Agent 产品的基本单位

大模型是概率系统，上下文也有限。每次派发给模型的任务，最好都有明确上下文、适中的工作量和可以确认的结果。

在 Agent Flow 里，每个 Node 就是一个最小任务单元：

- 输入是什么；
- 允许调用什么能力；
- 输出应满足什么契约；
- 失败以后重试、回退还是交给人；
- 完成后怎样把结果交给下一个节点。

单个 Node 可以保留模型的探索能力，整个 Flow 则保留系统的确定性。我们不是消灭 Agent 的自由，而是把自由放在适合它的边界里。

## 为什么用户会选择你的 Agent

原因通常只有两个。

第一，你拥有别的 Agent 拿不到的能力。真实业务数据、内部状态、可靠接口、权限和反馈闭环，往往比模型本身更稀缺。没有这些东西，再聪明的模型也只能停在聊天层。

第二，你真的能解决问题。三个按顺序执行的 LLM Call 加两个 API，如果可以稳定完成客户任务，就比一个华丽但不可复现的通用架构更有价值。

Agent 的成功标准不是架构图多漂亮，而是任务能否完成、成本是否可承受、用户是否愿意继续使用。

## Hardcode 是美丽的

过去我们排斥 hardcode，因为人工写代码和长期维护都很贵，于是不断追求抽象、复用和平台化。

LLM 让这个经济前提发生了变化。代码变便宜，针对真实场景编排一条 Flow 也变便宜。对模型来说，十个清楚的条件分支有时比一套为了未来可能性设计的抽象工厂更容易理解和修改。

如果一个客户的问题，用固定审批链路就能解决，那就先把链路写清楚；如果一份周报只需要几个稳定数据源和一次模型总结，就先让它每周可靠地产生。

这不等于鼓励无边界的复制粘贴。好的 hardcode 仍然需要明确输入输出、失败路径、测试、监控和所有者。它只是拒绝在问题尚未解决、客户尚未验证之前，提前为想象中的通用性支付复杂度。

## AI Native 不是给旧产品贴聊天框

AI Native 的核心很朴素：从模型的新能力出发，重新设计用户怎样完成任务。

不是让产品看起来有 AI，也不是强迫用户学习 Agent、Loop、RAG 和 MCP。用户说出目标以后，系统能以更低的认知负担把任务跑通，并且结果可靠、成本合理，这才有意义。

因此，一个 AI Native 产品经常会同时包含：

- 自然语言入口；
- 显式 Flow 和状态机；
- 能力明确的 Agent Node；
- 业务 API、数据和权限；
- 必要的 hardcode；
- 人工确认、验证与失败恢复。

Agent 只是能力之一，不是一切。

## 基础设施必须对模型友好

研发 Agent 也遵循同样的规律。模型能不能修 Bug，不只取决于智力，还取决于它能否读取日志、定位代码、调用测试、获得必要权限，并把验证结果带回任务。

当每个系统都只为人类点击设计，人就会变成 Agent 和基础设施之间的胶水：复制日志、申请权限、切换后台、截图，再把结果喂回模型。真正有价值的 Harness，不只是包住模型，还要让工具、权限、状态和证据形成一条可执行链路。

这也是组织需要变薄的地方。任务经过的转述越多，目标损耗越大；权限链路越长，Agent 越难形成闭环。所谓扁平，不是大家坐得近，而是目标、上下文、权限和反馈可以更短、更可靠地到达执行者。

## 通用能力什么时候才值得做

我并不反对通用组件。身份、权限、观测、重试、评测和基础工具当然应该复用。

真正危险的是：在还没有跑通几个具体问题之前，就把“做一个通用 Agent”当成目标。通用能力应该从多个已经验证的具体 Flow 中长出来，而不是从架构师对未来的想象里一次性设计出来。

先解决问题，再观察哪些部分反复出现；先允许 hardcode，再把稳定重复的部分抽象出来。这个顺序不能倒。

## 回到 Agent Flow

我做 Agent Flow，不是为了证明 Flow 比 Agent 先进，而是为了把 Agent 放回正确的位置。

直接从用户问题出发。确定的部分用确定的方式解决，需要模型判断的部分再交给模型。哪怕实现里有 if/else、固定 LLM Call 和业务接口，只要它能更简单、更可靠地完成任务，就是好方案。

不要在无尽的技术名词里游泳。去做一条真正能跑通、能失败、能恢复、有人愿意使用的链路。
