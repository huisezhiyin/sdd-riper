# 把工程任务交给 Agent：大模型时代程序员的身份与能力往哪迁移

> 我之前已经写过 Harness Engineering，也写过 SDD-RIPER 的落地方法。这篇不再重复定义。它想讲另一件事：好好用 Agent 写工程，第一步不是学会更多 Prompt，而是学会放权。
>
> 我回看过一批自己本地 Codex 的对话日志。日志本身不是重点，重点是它让我看见一个反复出现的模式：真正有效的协作，不是我把每一步都规定好，而是我逐渐把任务推进权交给 Agent，再用地形、checkpoint、反馈和经验沉淀把它接住。
>
> 这篇想讲清楚一个变化：代码实现可以越来越多地交给 Agent，程序员的核心能力要从连续实现，迁移到任务设计、过程控盘和交付验收。
>
> 任务包、checkpoint、反馈和经验沉淀，都是为这件事服务的。它们不是最终目标，最终目标是让人能把工程任务交给 Agent，同时仍然守住方向、风险和质量。

## 1. 很多人不是不会用 Agent，而是不敢放权

很多人已经开始用大模型写代码，但真实效果差异很大。

常见的用法有三种反模式。

第一种是把它当代码补全器：问一句，改一点，复制一段，人工再修一遍。模型确实帮忙了，但它没有进入工程任务本身。

第二种是把它当黑盒外包：把一个大需求整包丢过去，等模型说“完成了”，再面对一大坨自己也不敢合并的 diff。

第三种是持续微操：文件让它改哪几个，函数让它怎么写，遇到报错立刻手工接管，模型每一步都要等人指令。这样看似安全，实际会压掉强模型最有价值的探索能力。

真正的分水岭不是“会不会写 Prompt”，而是：**你敢不敢把一部分任务推进权交给 Agent。**

这里的放权，不是放飞。

放飞是把风险交给随机性。放权是承认强模型已经具备一定任务主体性，让它自己读地形、找入口、比较方案、发现隐藏约束、提出验证路径；同时，人把目标、边界、反馈和收束方式设计好。

最近做的几个项目，底层都指向同一个问题。无论是 [`sdd-riper-one-light`](https://github.com/huisezhiyin/sdd-riper/tree/main/skills/sdd-riper-one-light)，还是本地多 Agent 聊天室 [`adaptive-room-harness`](https://github.com/huisezhiyin/adaptive-room-harness)，还是经验资产本地化项目 [`agent-experience-capitalization`](https://github.com/huisezhiyin/agent-experience-capitalization)，都绕不开这件事：

**怎样让 Agent 承担更多自主任务能力，同时减少人类高频介入。**

这不是为了让文章听起来更前沿，而是为了提效。

我自己的使用方式，已经接近一种“Agent 化交付”。

也就是不再让 AI 只补几行代码，而是把一个完整的小工程任务交给它推进：

```text
人负责定义任务、准备上下文、设置边界、验收结果。
Agent 负责阅读、拆解、实现、修错、补验证、回写结论。
```

当这套方式跑顺以后，人不再被单个代码任务长时间锁死。一个 Agent 在改代码时，我可以去梳理另一个任务，或者启动另一个 Agent 做调研、审查、复盘。人的工作从单线程写代码，变成多线程控盘。

提效发生在这里。

关键不只是某次模型写代码比我快，而是我可以把越来越多“可包装、可验收、可回收”的工程任务交给 Agent 去推进。

我回看自己的 Codex 日志时，有几个模式很明显。

第一，顺的任务，很少是一上来就改代码。通常都是先读项目地形，先复述目标和风险，再进入实现。

第二，出问题的任务，往往不是模型不会写代码，而是它太早进入了执行。目标没对齐，边界没说清，验证也没想好，后面就只能靠人不断补救。

第三，最省力的时刻，不是模型一次写对，而是它能自己根据测试、日志、diff 继续收敛。这个时候人不用一直盯细节，只要看它有没有拿出可信证据。

第四，产生复利的任务，最后往往会留下一点东西：一条规则、一个测试入口、一段 README、一份 spec、一个经验资产。它们不是任务的核心目标，但会让下一次放权更稳。

这些不是多高级的理论，更像是我反复踩出来的使用习惯。写成文章，是希望别人少走一点弯路。

## 2. 放权之后，人类不是退场，而是换位置

我很喜欢“骑手和马”这个比喻。

一匹马真正跑起来的时候，骑手不应该替它迈腿。骑手替马迈腿，不但荒唐，而且会毁掉马的速度和力量。

但骑手也不是坐在马背上闭眼祈祷。

骑手要选赛道，控节奏，看风险，知道什么时候让马冲，什么时候勒住，什么时候转向，什么时候停下来检查。马负责速度、力量和现场反应，骑手负责方向、边界和最终判断。

Agent Coding 也是这样。

强模型已经不太像“更聪明的代码补全器”。它会自己读代码，自己找调用链，自己比较方案，自己发现文档不一致，自己提出测试入口。它不是完全可靠的工程师，但也不再是静止工具。

人类如果还坚持每一步都预设好，就像骑手替马迈腿。

反过来，如果人类完全不控方向，也会很危险。马跑得越快，越需要骑手有方向感和风险感。Agent 越强，越需要人有更好的控盘能力。

这类工程协作，不是“人写代码，AI 辅助”，也不是“AI 全自动，人旁观”。更准确的说法是：

```text
Agent 负责推进。
人负责控盘。
工程系统负责提供地形、边界、反馈和记忆。
```

![马与骑手：Agent 时代的人机协作关系](assets/agent-rider-horse.png)

放权不是人的价值下降，而是人的职责上移。

以前人更像执行者。现在更像骑手、教练、验收者和地形设计者。

## 3. 程序员的能力结构必须迁移

这件事背后有一个更大的变化：以前的软件工程时代，正在结束。

不是说代码不重要了，也不是说基础能力不重要了。恰恰相反，基础能力仍然决定你能不能判断 Agent 的输出是否可靠。

但程序员最稀缺的能力，正在从“亲手实现每一行”迁移到“定义任务、组织上下文、约束边界、验收结果、沉淀经验”。

过去，一个强程序员的优势，往往体现在：

- 代码写得快；
- 细节记得牢；
- 熟悉框架和 API；
- 能长时间沉浸在一个实现线程里；
- 能靠经验把 bug 一路追到底。

这些能力仍然有价值，但它们不再足够。

强模型加入之后，代码实现本身正在变得更便宜。一个合格 Agent 可以在很短时间里读代码、改代码、补测试、修失败。人如果还把主要精力放在“我比模型更快地写完这段实现”上，迟早会被新的交付方式压缩空间。

新的核心能力更像这样：

- 能把模糊需求整理成 Agent 可执行的任务包；
- 能判断哪些上下文必须先给，哪些可以让 Agent 自己找；
- 能在 checkpoint 里看出方向是否偏了；
- 能设计验证方式，而不是只听“完成了”；
- 能在多个 Agent 任务之间切换，保持全局节奏；
- 能把一次任务产生的经验沉淀成下一次的地形。

这不是“不会写代码也能当程序员”的意思。

恰恰相反，越是把实现交给 Agent，人越需要技术判断。因为你不再只是审一行代码，而是在判断一个任务包是否完整、一个方案是否越界、一个测试是否足够、一个结果是否能交付。

旧时代的程序员，核心身份是实现者。

新时代的程序员，核心身份会越来越接近任务设计者、系统控盘者和交付验收人。

如果还停留在“AI 帮我写几行代码”的心智里，很容易低估这次变化。真正发生的不是工具增强，而是交付结构变化。

以前是人亲自推动代码前进。

现在是人设计任务轨道，让 Agent 推动代码前进。

这也是为什么“放权”不是一个可有可无的技巧。它是程序员身份迁移的起点。

## 4. 让水先流动，不是让水乱流

过去我们理解软件工程，很容易把它想象成“挖水渠”。

人先规划好路线，水从哪里来，流到哪里，中间经过哪些田，哪里要分流，哪里要拦住，最好一开始就设计清楚。对应到软件研发里，就是先需求分析，再系统设计，再任务拆分，再实现、测试、上线。

这种方式没有错。在非大模型时代，这几乎就是工程理性的来源。因为真正会流动、会判断、会迁移的主体主要是人。工具只是工具，编辑器不会自己理解系统，也不会自己发现路线。

但强模型出现之后，“水”本身变了。

模型不再只是被动流过水渠的水。它会自己寻找坡度，自己试探支流，自己发现哪里堵住了，哪里有更短路径，哪里需要补桥，哪里原来的地图是错的。

这时候，如果人还是一开始就把所有路径都挖死，反而可能浪费强模型最有价值的探索能力。

更合适的工作方式是：**先让水流出来。**

不是放任水乱流，而是在一块有地形、有边界、有反馈的土地上，让水先漫出来，看它会自然形成哪些河道。等河道出现之后，人再去判断哪里值得修堤，哪里需要设闸，哪里可以开垦成田。

放权的真实含义是：

```text
不是提前规定每一步路径。
而是设计地形、边界、反馈和收束方式。
```

![地形与水流：把任务交给 Agent 之后，工程协作如何变化](assets/agent-terrain-flow.png)

Agent 先流动，人才看得见它的能力边界，也看得见任务真实的复杂度。

很多隐藏问题，不是在一开始写计划时暴露的，而是在 Agent 进入项目之后暴露的。一次 README 更新，可能会牵出 skill 的说明也要同步；一次 issue 回复，可能会暴露项目缺少最小接入方式；一次回归失败，可能会推动补日志、补测试脚本、补响应时间统计；一次“这个口径不对”，可能会让整个项目叙事从重 SDD 转向 Light Harness。

这些事情不是我预先排好完整流程表，然后模型机械执行。更真实的情况是：事件在我、模型、仓库、文档、测试、issue、PR 之间来回流动。模型会探索，会推进，会暴露问题，会生成路径。我的角色不是消失，而是判断这些流动里哪些有价值，哪些有风险，哪些应该固化成项目资产。

## 5. 放权的前提，是先让 Agent 进入地形

很多人一上来就对 Agent 说：

```text
帮我实现这个功能。
帮我修这个 bug。
帮我重构一下。
```

这当然可以，但它经常会让 Agent 直接从空中跳进执行阶段。它还没看见地形，就开始开挖。

更稳定的启动方式，是先让 Agent 进入地形。

它应该先读 README、AGENTS、相关 spec、代码入口、最近 diff、测试脚本、日志或截图。读完之后，不急着改代码，而是先复述：

```text
先不要改代码。
请先阅读相关上下文，告诉我：
1. 你理解的目标是什么
2. 当前代码大概怎么实现
3. 可能影响哪些文件
4. 最大风险是什么
5. 你准备用什么方式验证
```

这一步不是形式主义。

它的作用不是让流程显得严谨，而是让 Agent 先进入现场。只有进入现场，它的自主性才有意义。否则所谓“自主”，只是让一个没有地图的人跑得更快。

这也是为什么我不太愿意把很长的业务说明直接塞进 Prompt，然后期待模型一次性理解。Prompt 当然重要，但 Prompt 更像一次性的引导。能长期复利的，是地形。

在我的实践里，地形不是抽象词。它就是那些让 Agent 能稳定工作的工程资产：

- `AGENTS.md` 是项目级行为边界；
- `skills/` 是可复用能力入口；
- `spec / micro_spec` 是任务级真相源；
- `codemap` 是代码地形图；
- 测试集和日志是反馈仪表盘；
- README、issue、PR 是团队和外部用户的入口；
- 经验资产是下一次任务开始前可召回的项目记忆。

Prompt 解决的是“这一次模型怎么理解”。

地形解决的是“这个项目以后怎么稳定地让 Agent 工作”。

## 6. 怎样把一个任务交付给 Agent

如果要让别人真的学会，不能只讲“放权”，还要把放权拆成可执行动作。

![从“帮我修一下”到 Agent 可自主推进的任务包](assets/agent-task-package.png)

我通常会把一个工程任务包装成五件东西：

```text
目标：这次到底要完成什么。
上下文：Agent 需要先读哪些材料。
边界：哪些可以改，哪些不要碰。
验收：什么证据能证明做对了。
回收：完成后哪些经验要沉淀下来。
```

这五件事准备好，任务才适合交给 Agent。

很多人用 Agent 效果不好，是因为只给了目标：

```text
帮我修一下这个 bug。
```

这句话缺了四样东西：上下文、边界、验收、回收。

更好的方式是：

```text
目标：修复导入失败导致的测试报错。
上下文：先读 README、AGENTS、相关测试文件和报错日志。
边界：优先做最小修复，不要重构模块结构。
验收：跑指定测试命令，说明失败是否消失，有没有新增失败。
回收：如果发现项目测试入口或导入规则不清楚，补到文档或经验记录里。
```

这不是多写几句话的问题。

这是在把一个模糊请求，变成 Agent 可以自主推进的任务包。

你下次真的可以从这里开始试。

不要选最复杂的需求，也不要选纯聊天问题。选一个平时会让你打开 IDE 改半小时到两小时的小任务：一个测试失败、一个文档缺口、一个范围明确的 bug、一个小的兼容性问题。

然后不要急着让 Agent 写代码。先把这五件事丢给它，让它读完后复述。你会很快发现，任务是否能交出去，往往在复述阶段就能看出来。

如果它复述不清楚，先不要让它改。

如果它说不出验证方式，也先不要让它改。

如果它一上来想顺手重构很多东西，也先不要让它改。

这些地方拦住，后面会省很多时间。

任务包清楚以后，Agent 就可以自己读、自己找、自己改、自己验证。人不需要一直在旁边回答“这个文件能不能动”“这个测试要不要跑”“这里算不算完成”。

提效的关键，不是把 Prompt 写得更长，而是把任务交付格式变得稳定。

我会把它理解成一个很简单的交付循环：

```text
打包任务 -> Agent 推进 -> checkpoint 控盘 -> 证据验收 -> 经验回收
```

这套循环跑熟以后，人才有可能同时推进多条任务线。

因为人不再占用在每条任务的连续执行里，而是只在几个关键点出现：

- 任务开始前，判断目标和边界；
- 代码修改前，审 checkpoint；
- 执行完成后，看验证证据；
- 任务结束后，决定是否沉淀经验。

“多线程”的来源在这里。

不是人脑同时写多份代码，而是多个 Agent 在不同任务上执行，人类在关键节点切换上下文、做判断、收结果。

## 7. 不微操，但必须 checkpoint

放权最容易被误解成“少管”。

放权不是少管，而是从高频微操，变成关键节点控盘。

如果每一步都告诉 Agent 怎么写，它就没有机会自己形成路径。可如果完全不设检查点，它也可能越跑越偏。中间状态就是 checkpoint。

改代码前的 checkpoint 不用很长，但必须说清楚：

```text
改之前先给我：
1. 文件清单
2. 修改意图
3. 最小实现方案
4. 明确不做什么
5. 验证计划
```

这五项背后其实对应五个风险。

文件清单，是为了防止影响面无意识扩大。

修改意图，是为了确认 Agent 没有把任务理解歪。

最小实现方案，是为了避免它一上来重构半个系统。

明确不做什么，是为了给任务设边界。

验证计划，是为了让“完成”不只是一句自然语言总结。

这就是骑手的位置：不替马迈腿，但在关键路口必须知道它要往哪里跑。

## 8. 什么时候放开，什么时候收紧

放权不是固定强度。

我会用一个简单的判断：

```text
控制强度 = 任务风险 * 地形不确定性 / 反馈速度
```

这不是数学公式，只是帮助判断。

如果任务风险低、地形清楚、反馈很快，就可以放开。比如改一个小 bug、补一个文档入口、修一个单文件逻辑，只要 Agent 已经读过上下文，给一个 checkpoint，再让它自己完成，通常是合理的。

如果任务风险高、地形不清楚、反馈很慢，就应该收紧。比如鉴权链路、数据迁移、跨项目联动、线上兼容性、团队口径调整，这些任务就不能只靠一句“你自己看着办”。这时候需要 Research，需要 micro-spec，需要 Plan，需要 Approval，需要更明确的验收标准。

我不反对重流程，也不迷信轻流程。

我反对的是控制强度和任务风险不匹配。

很多人用 Agent 不稳定，不是因为模型一定不行，而是因为他们该放开的时候微操，该收紧的时候放飞。

一种常见错误是：讨论阶段急着让 Agent 干活。目标还没对齐，事实还没读完，风险还没浮出来，就开始改代码。

另一种常见错误是：执行阶段又让 Agent 重新自由发挥。明明 Plan 已经确认，边界已经定好，却在实现时不断打开新问题、新方案、新范围。

好的协作应该反过来：

```text
探索阶段，给 Agent 更多空间。
执行阶段，给 Agent 更清楚的边界。
验收阶段，给 Agent 更硬的证据要求。
```

这也是我区分 [`sdd-riper-one-light`](https://github.com/huisezhiyin/sdd-riper/tree/main/skills/sdd-riper-one-light) 和标准 [`sdd-riper-one`](https://github.com/huisezhiyin/sdd-riper/tree/main/skills/sdd-riper-one) 的方式。

[`sdd-riper-one-light`](https://github.com/huisezhiyin/sdd-riper/tree/main/skills/sdd-riper-one-light) 不是“简化版”，而是强模型时代更自然的默认入口。它承认模型有探索能力，通过 restate、checkpoint、validation、reverse sync 来控盘，而不是把所有阶段文本都常驻塞给模型。

标准 [`sdd-riper-one`](https://github.com/huisezhiyin/sdd-riper/tree/main/skills/sdd-riper-one) 也不是“落后版本”。它更重、更显式，适合训练、审计、交接、高风险任务和团队过渡。

Light 负责让强模型跑起来。

标准版负责在风险更高时把控制显式化。

## 9. 验收 Agent，不要只听“完成了”

Agent 最危险的时刻，往往不是它报错。

报错反而好，因为报错是一个反馈面。

更危险的是它把“阶段性完成”说成“任务完成”，把“代码改了”说成“需求完成”，把“测试跑过一个入口”说成“风险关闭”。

“测试通过”还不够。我会继续追问：

```text
请给出：
1. 实际改动摘要
2. 跑过的验证命令
3. 验证结果
4. 哪些目标已覆盖
5. 哪些风险尚未覆盖
6. 如果失败，下一步定位路径是什么
```

AI 参与之后，失败点会变得更分散。它可能不在某一行代码里，而在上下文注入、能力召回、Prompt 约束、工具调用、运行态摘要、SSE 流、测试脚本统计方式里。

Agent 工程必须有 feedback surface。

没有反馈面，水流再强也只是冲刷。

测试、日志、lint、diff、review、截图、trace、响应时间、错误归因，这些不是形式。它们是让 Agent 能够自主修正的地面回声。

一个没有反馈面的 Agent，只能靠人类盯盘。

一个反馈面足够清楚的 Agent，才可能承担更多任务推进责任。

## 10. 协作房间和经验资产，只是为了让放权更稳

下面这一段先打个预防针：以下个人项目属于王婆卖瓜，大家有空可以赏脸试试看，但并不是必须使用的产品。它们都还在 pre 阶段，更适合当玩具、样例和思路参考，不建议直接带进生产环境。你完全可以用自己的脚本、文档、CI、review 流程，做出类似的承接层。这里放出来，只是为了说明我自己是怎么把“放权”落到工程里的。

人类减少高频介入，不是靠忍住不说话。

如果系统没有承接能力，人不介入只会变成失控。

我做这些项目，本质上是在补“放权之后的承接层”。它们不是这篇文章的核心目标，核心目标仍然是：把工程任务交给 Agent，让人从连续实现线程里抽出来，转向任务设计、过程控盘和交付验收。

所谓承接层，就是在人不持续盯着时，系统里要有别的东西帮忙接住任务，比如同伴审查、验证证据、历史经验和可回读的文档。

比如 [`adaptive-room-harness`](https://github.com/huisezhiyin/adaptive-room-harness)，我用它处理复杂任务里的协作承接。

主 Agent 仍然是任务 owner、final decider、writer、verifier。但当任务复杂、风险高、信息不确定时，它不一定每次都要等人类高频追问。它可以唤醒一个本地多 Agent 房间，让其他 Agent 做讨论、审查、挑战假设、补外部视角，最后沉淀成 `main_agent_reference.json` 这样的参考包。

这不是把任务交给一群 Agent 乱跑。

它的关键是：主 Agent 仍然控盘，房间提供 advisory input。也就是让 Agent 系统内部多一些自我讨论和自我校验能力，减少人类在每个分岔点上的手动介入。

再比如 [`agent-experience-capitalization`](https://github.com/huisezhiyin/agent-experience-capitalization)，我用它处理经验承接。

Agent 每次任务结束后，不一定都要沉淀资产。小任务做完就结束也很正常。只有当这次任务暴露了稳定规则、常见坑、测试入口、项目约定或反模式时，才值得把它沉淀成项目或团队拥有的工程资产。未来任务开始前，Agent 可以自动召回相关经验，再由当前模型结合上下文判断是否采用。

这件事非常重要。

很多人所谓“用 Agent 很累”，本质上是每次都在重复喂同样的背景、同样的规则、同样的坑。Agent 不累，人累。

如果经验不能沉淀，放权每次都要从零开始。

经验能沉淀，放权才会变稳。

Agent 自主任务能力不是单纯靠模型智商提升出来的。它来自一组工程承接层：

- 有地形，Agent 才能进入项目；
- 有 checkpoint，Agent 才能安全推进；
- 有反馈面，Agent 才能自我修正；
- 有协作房间，Agent 才能在复杂任务里获得第二视角；
- 有经验资产，Agent 才能不从零开始。

这些东西组成了放权的基础设施。

## 11. 一次任务应该怎么跑起来

如果把上面的东西压到一次真实工程任务里，它大概不是“发一个神仙 Prompt，然后等结果”。

更像下面这种节奏。

第一步，不急着改。

我会先让 Agent 读地形。它要知道这个项目是什么，当前任务从哪里进，已有约束是什么，验证入口在哪里。这个阶段可以让它多探索一点，因为很多时候人也不完全知道所有相关文件在哪里。

这时候人的问题不是“你准备怎么写代码”，而是：

```text
你现在看到的系统结构是什么？
这个任务可能会碰到哪些边界？
你认为最小改动路径是什么？
有哪些地方需要先确认？
```

第二步，让它交代路线。

如果它准备动代码，我会要求 checkpoint。不是为了让它写长篇计划，而是为了确认它没有跑错方向。

一个好的 checkpoint 应该让我在几十秒内判断三件事：它懂不懂目标，它有没有扩大范围，它知不知道怎么证明自己做对了。

第三步，让它自己推进。

只要 checkpoint 过了，我不会每一行都指挥。强模型的价值就在这里：它能自己找入口、拆局部任务、修失败、补漏掉的引用、根据测试结果迭代。人如果在这时高频插手，往往会把 Agent 的连续推理打断。

这一步最像骑手放开缰绳，让马真的跑起来。

第四步，用反馈收束。

Agent 说完成之后，我不会只看“完成了”三个字。我看 diff，看测试，看日志，看它有没有说明未覆盖风险。必要时，我会让它重新解释失败路径，或者让它只针对某个失败点继续收敛。

第五步，决定要不要修河床。

如果这次任务只是一次性小改动，可能到这里就结束。但如果它暴露了项目规则、测试入口、常见坑、文档口径、协作约定，那就不应该只留在聊天记录里。

它应该进入 README、AGENTS、skill、spec、checklist，或者经验资产。

差别就在这里：这次任务有没有变成下次任务的地形。

很多人想让 Agent 更自主，但只关注任务执行本身。真正决定自主性的，是任务前后的这两段：前面有没有地形，后面有没有沉淀。

中间那段执行，反而是模型最擅长的。

## 12. 如果你想直接开始

如果只看理念，很容易停在“好像懂了，但明天还是不知道怎么用”。

不建议一上来就自己发明流程。更简单的方式，是先用已经整理好的 Skill。

这些 Skill 已经整理在 GitHub 仓库里：[huisezhiyin/sdd-riper](https://github.com/huisezhiyin/sdd-riper)。仓库根目录也放了一个脱敏后的 [`AGENTS.md`](../AGENTS.md)，可以直接看项目级行为边界应该怎么写。

这套工作法有两个入口：

- [`sdd-riper-one-light`](https://github.com/huisezhiyin/sdd-riper/tree/main/skills/sdd-riper-one-light)：日常默认入口，适合大多数 Agent Coding 任务；
- [`sdd-riper-one`](https://github.com/huisezhiyin/sdd-riper/tree/main/skills/sdd-riper-one)：标准控盘入口，适合复杂、高风险、需要审计和交接的任务。

如果你刚开始，不要先纠结完整方法论。先记住 Light 的节奏就够了：

```text
先读地形 -> 复述目标和风险 -> 给 checkpoint -> 执行 -> 验证 -> 回写
```

它对应到本文的五件事就是：

```text
目标：让 Agent 复述它理解的任务。
上下文：让 Agent 先读 README、AGENTS、代码入口、日志或测试。
边界：让 Agent 在 checkpoint 里说明改哪些、不改哪些。
验收：让 Agent 给出测试、日志、diff 或其他证据。
回收：让 Agent 判断要不要更新文档、规则、skill 或经验资产。
```

你可以从一个很小的任务开始，比如修一个测试失败、补一个文档入口、改一个明确的 bug。

不要一开始就拿“重构整个系统”练手。先从半小时到两小时能验证完的小任务开始，最容易体会到这套方式为什么省力。

我的建议是，第一次用的时候不要贪多。你只要练三件事：

```text
先让它读。
改之前让它说计划。
改完让它拿证据。
```

这三件事做稳了，已经比大多数“帮我写一下”的用法强很多。

第一句话不要说：

```text
帮我修一下。
```

换成：

```text
请按 sdd-riper-one-light 的方式处理这个任务。
先不要改代码。
先读相关上下文，然后复述目标、风险、可能影响的文件和验证方式。
```

等它复述完，再让它给 checkpoint：

```text
在改代码前，请给我：
1. 文件清单
2. 修改意图
3. 最小实现方案
4. 明确不做什么
5. 验证计划
```

如果这个 checkpoint 你看得懂，而且范围合理，就让它执行。

执行完不要只听它说“完成了”，继续问：

```text
请给出：
1. 实际改动摘要
2. 跑过的验证命令
3. 验证结果
4. 哪些目标已覆盖
5. 哪些风险尚未覆盖
6. 是否需要回写 README、AGENTS、spec、skill 或经验资产
```

这就是最小闭环。

不用一开始就追求完美，也不用马上把所有项目都改造成完整 Harness。先用这个小闭环跑几次，你会很快感觉到区别：你不再是一步步推着 Agent 写代码，而是在让它自己推进，你只在关键位置判断方向、范围和证据。

什么时候切到标准 `sdd-riper-one`？

很简单：当你觉得“这事如果错了代价很大”，就收紧。

比如：

- 涉及鉴权、支付、数据迁移、权限、线上兼容；
- 一次要改很多文件或多个仓库；
- 需要别人 review、交接或审计；
- 模型和你对需求理解不一致；
- 没有可靠测试，反馈很慢。

这些时候，不要硬用 Light 往前冲。切到标准控盘入口，让 Research、Plan、Approval、Review 更显式一点。

这篇文章讲的是为什么要放权，以及放权之后人该怎么控盘；Skill 解决的是怎么把这些动作变成 Agent 每次都能执行的工作约定。

初始接入时，就从一句话开始：

```text
请按 sdd-riper-one-light 的方式处理这个任务，先读上下文并复述，不要急着改代码。
```

这一步做对，后面会稳很多。

## 13. 最后要修河床

一次 Agent 任务如果只留下聊天记录，就是水流过去了。

它可能当时很精彩，模型找到一个好路径，修了一个难 bug，补了一处隐藏风险。但如果这些东西只留在对话里，下次很可能还要重新来一遍。

有复利的是修河床。

也就是任务结束后问自己：

- 这次确定的项目规则，要不要写进 `AGENTS.md`？
- 这次踩过的坑，要不要沉淀成经验资产？
- 这次稳定的操作方式，要不要变成 skill？
- 这次验证入口，要不要写进 README 或测试文档？
- 这次业务边界，要不要写进 spec？
- 这次 review 发现的风险，要不要成为 checklist？

这不是文档洁癖。

这是在把一次水流变成下一次可复用的河床。

强模型时代，人的高价值动作不只是“把这次任务做完”，而是看见哪些路径值得固化，哪些风险值得设闸，哪些经验值得沉淀，哪些地形需要重修。

我想要的不是完全放飞模型，也不是把模型锁回旧流程。

我想要的是中间这条路：

```text
让 Agent 先跑起来。
让我观察它的水势。
在关键位置握住缰绳。
用反馈判断它是否跑对。
把有效路径修成河床。
把经验沉淀成下一次的地形。
```

好好用 Agent 写工程，训练的不是写 Prompt 的能力，而是带一个非确定性执行主体完成交付的能力。

这件事的第一步，就是学会放权。

不是放弃控制，而是把控制从高频微操，升级成地形、边界、反馈、协作和记忆。

Agent 负责跑。

人负责看懂它为什么这样跑，什么时候该让它继续，什么时候该拉住，什么时候该把跑出来的路修成下一次的河床。

如果只记住一个动作，那就是：下次不要只给 Agent 一个目标，试着同时给它目标、上下文、边界、验收和回收。
