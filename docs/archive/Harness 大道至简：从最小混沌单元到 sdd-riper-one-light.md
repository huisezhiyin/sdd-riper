# Harness 大道至简：最小混沌单元与水流理论

> 这篇文章只讲两件事。
> 第一，真正的 AI Coding Harness 不是一套固定范式，而是先把任务切成适合大模型独立推进的“最小混沌单元”。
> 第二，任务交出去以后，人不微操过程，而是顺着大模型自己的设计思路和开发水流，维护边界、方向、证据和回炉判断。
> `sdd-riper-one-light` 和 `sdd-riper-one` 是这两件事的训练轮和护栏：它们不替代人的判断，只把 Spec、Checkpoint、Validation、Handoff、Archive 这些关键锚点固化下来。

## 30 秒定义

Harness 不是一套固定操作步骤，也不是一个更长的 Prompt。

Harness 是把一个可验证的任务单元交给大模型自主推进；人不微操过程，只维护目标、边界、权限、上下文、checkpoint 和验收证据。

它只回答四个问题：

| 问题 | Harness 的回答 |
| --- | --- |
| 任务怎么交出去 | 切成模型能独立推进的最小混沌单元 |
| 过程怎么不失控 | 关键节点 checkpoint，而不是逐行遥控 |
| 完成怎么判断 | 用测试、日志、截图、人工验收等证据证明 |
| 下次怎么接上 | 用最小 spec / summary / handoff 留下可恢复上下文 |

所以最简单的工作分工是：

```text
人负责目标、边界、节奏、风险和验收；
模型负责探索、实现、修复和推进；
spec 是持久化真相源，不是反复塞满上下文的大 prompt。
```

落到本仓库，就是两层 skill：

- `sdd-riper-one-light`：给熟练用户和日常任务用，轻提示、中度留痕、checkpoint、validation、reverse sync。
- `sdd-riper-one`：给新手、复杂任务、高风险任务、审计交接用，更明确的阶段门禁、codemap / context、完整 spec、更多问询与阻塞。

## 一、先把话说透：Harness 不是律令

我一直不太愿意把 AI Coding 写成一套固定范式。

原因很简单：今天的大模型已经足够强。它可以读代码、拆任务、写实现、跑测试、解释日志、修复错误。越是强模型，越不应该被重新绑回一套死流程里。

真正的 Harness，不是规定模型必须第一步做什么、第二步做什么、第三步做什么。

真正的 Harness 是人学会判断：

- 这个任务应该切多大。
- 哪些信息要先给模型。
- 哪些边界必须提前说死。
- 哪些地方可以让模型自由探索。
- 哪些节点必须停下来 checkpoint。
- 什么证据能证明任务完成。
- 什么时候应该归档经验，让下一次不用重来。

所以我更愿意把 Harness 理解成一种控盘能力，而不是一套操作说明书。

最简单的一句话是：

> Harness 就是把一个可验证的任务单元交给大模型自主推进；人不微操过程，只维护目标、边界、权限、上下文和验收证据，并在偏航、失败或风险升高时决定校正方向或回炉。

如果一定要用一个比喻，强模型更像一匹有速度、有判断、有脾性的马，也像一股会自己寻找路径的水。

你不需要替它迈腿，也不需要替每一滴水指定路线。

你要做的是选方向、立边界、设闸门、看证据。

## 二、最小混沌单元：先确认任务边界

AI Coding 里最核心的能力，不是 Prompt 写得多漂亮，也不是工具装得多全。

真正核心的是：**能不能把一个任务切成合适大小的最小混沌单元。**

任务太大，模型会漂。

比如“做一个高并发直播系统”，里面包含聊天室、权限、禁言、礼物、红包、资金安全、消息链路、降级、监控、风控。你把它整个丢给模型，就是把一个巨大混沌系统直接扔进概率模型里。

任务太小，人又变成遥控器。

比如“写这一行”“改这个变量名”“再写下一行”，模型就失去了探索空间，人类也没有真正放权。

一个好的最小混沌单元，应该满足六个条件：

| 条件 | 说明 |
| --- | --- |
| 目标清楚 | 模型知道这轮到底要解决什么 |
| 边界可见 | 模型知道哪些地方不能顺手改 |
| 上下文足够 | 模型有足够信息判断代码地形和需求语义 |
| 结果能验 | 人能通过测试、日志、运行结果或人工验收判断完成 |
| 失败局部可重来 | 出错时不用推倒整个任务 |
| 模型有自主空间 | 不是把模型降级成打字员 |

这就是 Harness 的第一层：**切任务边界**。

只要任务切得好，按照今天的大模型能力，你怎么玩都可以。

你可以让它先研究，也可以让它先提方案；可以让它写 micro-spec，也可以让它直接给 checkpoint；可以让它跑测试，也可以让它先给人工验证清单。形式不是关键。

关键是：这个单元有没有被控制在“可理解、可验证、可回退、可继续探索”的范围内。

### 怎么判断一个大任务该不该继续拆

可以用这几个问题快速判断：

- 这一轮目标能不能用一句话讲清楚。
- 这一轮是否有明确 In / Out。
- 这一轮需要读的上下文是否能收拢到一组文件、一个链路或一个 context bundle。
- 这一轮完成后能不能用测试、日志、运行结果、截图或人工验收证明。
- 这一轮失败后，能不能局部回炉，而不是整件事全部推倒。
- 这一轮是否仍然给模型保留了方案选择、代码探索和实现组织的空间。

如果这些问题大多回答不了，就不是一个好的最小混沌单元。

这时不要急着写代码，应该先做三件事之一：

- 拆小任务。
- 补 codemap / context。
- 升级到更重的 spec 和 checkpoint。

## 三、水流理论：再顺着模型协作

最小混沌单元解决的是“什么可以交给模型跑”。

水流理论解决的是“交出去以后，人怎么和模型协作”。

很多人用 AI Coding 不舒服，是因为心里已经有一条固定实现路径，然后要求模型严格照这条路走。模型一旦提出不同做法，就觉得它跑偏了。

但强模型真正擅长的，恰恰不是当一个高级打字员。

它会读代码地形，会发现人没注意到的调用链，会根据测试失败调整方案，会在局部实现里找到更贴近现有系统的路径。这个时候，如果人的控制方式还是“我脑子里原来怎么想，你就怎么写”，就很容易把模型的能力压扁。

水流理论说的是：

> 人先给目标、边界、验收和风险闸门；模型在边界内按自己的理解探索路径；当模型发现更自然、更低风险、更贴近代码地形的做法时，人要允许原始设想被修正。

这不是放任。

放任是没有边界、没有证据、没有回炉。

水流是有河岸、有闸门、有水位线、有下游验收的。

所以人真正要盯的不是“模型有没有逐字照我的设想执行”，而是：

- 它有没有偏离核心目标。
- 它有没有越过边界。
- 它引用的事实是否成立。
- 它的方案是否比原设想更贴近代码地形。
- 它的验证证据是否足够。
- 它失败时是否能局部回炉。

这也是为什么 Harness 不应该写成死范式。

死范式会要求水按格子走。

好的 Harness 是修河道、设闸门、看流向。

## 四、那为什么还需要 sdd-riper-one-light

如果真正的 Harness 是心法，那为什么还要做 Skill？

因为不是每个人一开始就有这个手感。

很多人刚开始用 AI Coding，会自然滑向两种模式：

- 要么完全放飞，把大需求整包丢给模型。
- 要么完全遥控，让模型一步一步当打字员。

这两种都不是好 Harness。

`sdd-riper-one-light` 的意义，是给还没完全掌握手感的人一套轻量护栏。

它不负责替你思考，也不负责规定你每一步必须怎么走。

它只保留几个关键锚点：

| 锚点 | 作用 |
| --- | --- |
| Restate First | 先复述理解，避免一开始就跑偏 |
| Spec / micro-spec | 把目标、范围、完成定义落到外部文档 |
| Checkpoint | 执行前让人类设闸 |
| Validation | 完成必须由证据证明 |
| Reverse Sync | 把结论、偏差、风险回写 |
| Resume / Handoff | 长任务能换 chat、换人继续 |
| Archive | 把可复用经验沉淀成团队资产 |

这里面最硬的要求，是必须有外部真相源。

也就是至少要有一份 Spec、micro-spec、summary 或 handoff。不能让任务状态只活在聊天窗口里。

其他东西都是轻量护栏：任务越小越轻，任务越大越完整；风险越低越自由，风险越高越需要 checkpoint。

所以 `sdd-riper-one-light` 不是重流程。

它更像这样一句话：

> 你可以自由使用强模型，但不要丢掉目标、边界、证据和恢复点。

这套体系里其实有两个 Skill：

| Skill | 适合谁 | 核心作用 |
| --- | --- | --- |
| `sdd-riper-one-light` | 已经能和强模型高频协作的人，或日常中低风险任务 | 给模型保留水流空间，只固化最小锚点 |
| `sdd-riper-one` | 新手、复杂任务、高风险任务、需要审计或交接的任务 | 用更显式的 RIPER 阶段训练任务切分、边界确认和批准执行 |

简单说：

- light 假设你已经大致会切最小混沌单元，所以它只提醒关键锚点。
- one 帮你一步步建立这种判断，所以它更重、更显式、更适合训练和控风险。

## 五、Skill 到底怎么运行

`sdd-riper-one-light` 运行起来，很多时候是无感的。

它不会每次都打印一大堆阶段标题，也不会要求模型写一堆低价值过程文本。

它更像一个默认工作姿态：

```text
用户给任务
  -> Agent 先复述理解
  -> 判断任务大小和风险
  -> 小任务生成 micro-spec / summary
  -> 中大型任务生成 spec
  -> 陌生代码按需补 codemap / 地形摘要
  -> 复杂需求按需整理 context bundle
  -> 执行前给 checkpoint
  -> 获得批准或确认后执行
  -> 执行后给 validation
  -> 长任务收束为 handoff / archive
```

用久以后，你会觉得它没什么存在感。

但这恰恰是它最好的状态。

因为它已经把 Codex / Agent 的默认行为塑形成：

- 先读上下文。
- 先复述理解。
- 先明确目标和范围。
- 修改前先 checkpoint。
- 完成后给验证证据。
- 交代剩余风险。
- 长任务留下下一轮入口。

一旦没有这套默认姿态，差异会变明显：Agent 更容易裸改，更容易把“写完了”当成“完成了”，更容易忘记剩余风险，也更容易把上下文留在聊天窗口里。

## 六、会玩的人怎么用：自由，但不失锚

如果你已经有 Harness 手感，其实不用机械照流程。

你真正要做的是两件事：

- 先判断当前任务是否已经是一个最小混沌单元。
- 再判断模型提出的路径，是不是在边界内更顺水的做法。

### 1. 极小任务

比如 typo、文案、单点配置、无风险机械修改。

可以很轻：

```text
目标是什么
改哪里
怎么确认
```

这类任务不需要写完整 spec。

但最好仍然留一句 micro-summary，避免任务上下文消失。

### 2. 普通代码任务

比如一个 bugfix、一个小功能、一个局部重构。

推荐保留：

```text
Goal
Scope
Done Contract
Checkpoint
Validation
Change Log
```

这就是 `sdd-riper-one-light` 的日常主场。

### 3. 陌生老项目任务

不要直接开写。

先让 Agent 做地形摘要；如果需要完整 codemap、跨模块索引或可复用资产，就切到 `sdd-riper-one` 的 `create_codemap`：

```text
请使用 sdd-riper-one-light。
这是一个老项目里的新任务，先不要改代码。

请先基于当前目标做最小代码地形摘要：
- 入口在哪里
- 关键调用链是什么
- 相关配置 / 数据结构在哪里
- 可能影响哪些模块
- 当前最需要确认的风险点

如果你判断需要完整 codemap，请暂停并建议切到 sdd-riper-one / create_codemap。
```

codemap 不是为了好看，而是为了减少“模型没看懂地形就开始施工”的风险。

### 4. 复杂需求任务

如果需求来自 PRD、会议纪要、接口文档、聊天记录、截图，不要直接塞给模型写代码。

先让它整理最小 context；如果资料多、来源杂、需要长期复用，就切到 `sdd-riper-one` 的 `build_context_bundle`：

```text
请使用 sdd-riper-one-light。
先不要写代码。

请把这些需求资料整理成最小 context 摘要：
- 目标
- 用户场景
- 明确需求
- 非目标
- 已知约束
- 待确认问题
- 验收标准

如果你判断资料需要正式 context bundle，请暂停并建议切到 sdd-riper-one / build_context_bundle。
```

context 的价值，是把杂乱输入变成干净输入。

输入干净了，后面的 spec 和 checkpoint 才不会建在噪音上。

### 5. 高风险任务

涉及安全、权限、资金、数据一致性、状态机、并发时序、跨项目契约时，不要过度相信“轻”。

这时应该升级：

```text
micro-spec -> standard spec
单点 checkpoint -> 多轮 checkpoint
局部验证 -> 更完整验证
summary -> handoff / archive
```

必要时切到 `sdd-riper-one` 标准控盘版。

这里的原则不是“越重越好”，而是“风险越高，外部锚点越完整”。

### 6. 当模型提出和你原设想不同的路径

这时不要立刻打断，也不要立刻放行。

先让它补齐判断：

```text
你提出的方案和我原来的设想不同。

请先说明：
- 为什么这个方案更适合当前代码地形
- 它是否仍然满足本轮核心目标
- 它有没有改变 Scope
- 它的主要风险是什么
- 如何验证它确实更好
- 如果失败，如何局部回炉
```

如果它说得清，并且证据成立，就应该允许原设想被修正。

这就是水流理论的重点：人不执着于自己的第一条路线，而是守住边界和结果，让模型选择更亲和它能力结构的路径。

## 七、不会玩的人怎么用：先照范式跑

对于不太熟的人，最重要的是先跑起来。

不用理解全部心法，也不用背长 Prompt。

只要统一一个最小任务包：

```text
请使用 sdd-riper-one-light 处理这个任务。
先不要直接改代码。

目标：
范围：
约束：
验证：

请先给我：
- 你对任务的理解
- 本轮核心目标
- micro-spec / summary
- Done Contract
- 下一步动作
- 风险
- 验证方式

我批准后再执行。
```

这就是给初学者的固化范式。

它不是终点，而是训练轮。

先照它跑，目的是建立几个习惯：

- 不裸改。
- 不把任务做散。
- 不把“写完”当“完成”。
- 不让上下文只存在于聊天里。
- 不让经验在任务结束后消失。

等这些习惯长出来，你自然可以更自由。

## 八、几个真实例子

### 例子一：低版本运行时兼容问题

问题：编译期可见的新 SDK 方法，线上低版本运行时不存在，导致 `NoSuchMethodError`。

如果裸用 Agent，它可能直接建议升级 SDK、改调用方接口，或者扩大修改范围。

用 `sdd-riper-one-light` 时，任务先被切成一个小而清楚的单元：

```text
Goal:
  修复低版本运行时缺失方法导致的兼容问题。

Scope:
  In: 版本读取逻辑。
  Out: SDK 升级、调用方接口变更、缓存协议调整。

Done Contract:
  旧版本运行时不再触发 NoSuchMethodError。
  无法读取版本时稳定回退为 0。
  生产代码不再静态调用缺失方法。

Validation:
  静态检查确认不再直接调用缺失方法。
  测试覆盖无版本场景。
```

这个例子说明：小任务不需要重流程，但需要清楚的目标、范围和验证。它的最小混沌单元就是“版本读取兼容”，不是“升级 SDK”，也不是“重构调用链”。

对应脱敏示例：

- [spec-light-runtime-compat.md](../skills/sdd-riper-one-light/examples/specs/spec-light-runtime-compat.md)

### 例子二：安全状态时序冲突

问题：同一资源先被错误回写为放行状态，随后异步检测又修正为拒绝状态，客户端可能先消费错误状态。

这不是普通 bugfix，而是状态时序问题。

此时要升级成 standard spec：

```text
Goal:
  杜绝先放行、后拒绝的错误状态时序。

Scope:
  In: 上传阶段状态冲突、重复回写。
  Out: 客户端逻辑、下载链路策略、无关规则扩展。

Facts:
  已确认状态先后冲突。
  已确认旧兼容分支会提前回写。
  已确认新检测链路仍会异步修正状态。

Validation:
  日志中不再出现先放行后拒绝。
  单次状态更新不再双写。
  相关测试通过。
```

这个例子说明：复杂任务不是多写文档，而是要把事实、边界和验证提前锁住。状态时序问题天然容易扩散，所以要把任务单元收束成“杜绝先放行、后拒绝”，而不是顺手重做整个安全链路。

对应脱敏示例：

- [spec-standard-security-status-race.md](../skills/sdd-riper-one-light/examples/specs/spec-standard-security-status-race.md)

### 例子三：长链路任务交接

有一类任务不是改一个函数，而是连续推进一个平台化链路。

过程中会经历：

- 需求理解。
- 代码梳理。
- 多轮实现。
- 多轮测试。
- 外部接口错误。
- 字段映射问题。
- 状态语义调整。
- 配置或存储方案切换。
- 继续扩场景。

这种任务不能靠聊天记录保存上下文。

它需要 handoff：

```text
1. 这份文档的用途
2. 当前一句话结论
3. 当前稳定范围
4. 当前不稳定范围
5. 已完成事项
6. 当前核心技术判断
7. 当前接口 / 入口怎么用
8. 当前配置 / 存储状态
9. 已确认 bug 与已收敛结论
10. 建议测试口径
11. 关键代码入口
12. 关键提交
13. 未完成事项
14. 下一轮建议直接贴什么
15. 最终总结
```

这个例子说明：长任务不是靠模型记忆接住的，而是靠外部交接文档接住的。水可以继续往前流，但河道和水位要记录下来，否则下一轮就不知道自己从哪里接。

## 九、效果到底好在哪里

`sdd-riper-one-light` 的效果，不是让模型显得更有仪式感。

它真正带来的效果是这些。

### 1. 任务启动更稳

以前一句“帮我改一下”就进入代码，Agent 很容易先跑偏再补救。

现在先经过 `Restate / Goal / Scope / Done Contract`，很多误解会在执行前暴露。

### 2. 人类控制更轻

人不需要逐行遥控模型，只需要在 checkpoint 上判断：

- 目标是否对。
- 边界是否对。
- 下一步是否合理。
- 风险是否接受。
- 验证是否足够。

这比全程盯着模型写代码轻很多。

### 3. 模型路径更自然

水流理论会让人从“要求模型照我脑内路径写”切换成“让模型在边界内寻找更适合当前代码地形的路径”。

这会带来一个很明显的变化：模型不再只是执行器，而是会成为设计协作者。

它可以提出更小的修改面、更低风险的兼容方案、更贴近现有抽象的实现方式。

人要做的是审它的证据，而不是压平它的探索。

### 4. 验证意识更强

`Done by Evidence` 会逼 Agent 从“我写完了”转向“我用什么证明完成了”。

这会自然推动测试、日志、运行结果、人工验收进入交付闭环。

### 5. 经验开始沉淀

每次任务结束后，如果能留下 `Validation / Handoff / Archive`，那这次任务就不只是一次代码修改，而是下一次任务的上下文资产。

这也是 `sdd-riper-one-light` 真正成熟的地方：它不是追求一次性答案，而是让每次使用都能反过来增强团队上下文。

### 6. Codex 的默认工作姿态被塑形

在 Codex 这类 agentic coding 环境里，`sdd-riper-one-light` 的效果尤其像底层习惯：

- 默认会读项目规则和相关上下文。
- 中等以上任务会先对齐目标和范围。
- 修改前倾向于给 checkpoint。
- 不会轻易跨出任务边界。
- 执行后会报告验证跑了什么、没跑什么。
- 会提醒剩余风险，而不是只报喜。
- 长任务会倾向于留下 handoff / summary。

它不是每次都显式说“我正在运行 sdd-riper-one-light”，但很多稳定行为就是被这套 Skill 和仓库规则长期塑出来的。

这也是为什么熟练使用后会无感：不是它没运行，而是它已经变成默认工程姿态。

### 7. 团队协作从“靠人会用”变成“靠流程可复用”

个人熟练使用 AI，本质上还是个人能力。

`sdd-riper-one-light` 的价值在于把这种能力拆成团队可复用动作：

```text
任务输入 -> micro-spec -> checkpoint -> execute -> validation -> handoff/archive
```

新人不需要理解所有心法，先照这个闭环跑起来，就能避免最常见的裸改、跑偏、无验证、无交接。

这也是它适合扩散的原因：它不是要求每个人都成为 Prompt 高手，而是给每个人一套最小但稳定的 AI Coding 操作面。

### 8. 可量化指标怎么设计

如果团队要看数据，不建议只看 AI 代码占比。

更应该看这些指标：

| 指标 | 说明 |
| --- | --- |
| checkpoint 覆盖率 | 中等以上任务修改前是否有 checkpoint |
| validation 覆盖率 | 任务完成是否有测试、日志、运行结果或人工确认 |
| handoff 覆盖率 | 长任务是否留下恢复入口 |
| 返工轮次 | 从人工反馈到收敛需要几轮 |
| 恢复时间 | 新 chat / 新同学接手需要多久恢复上下文 |
| 越界修改次数 | 是否出现 Scope 外的无关改动 |
| 路径修正质量 | 模型提出不同方案时，是否有事实、风险和验证支撑 |
| archive 复用次数 | 历史经验是否被下一次任务复用 |

这些指标比“AI 写了多少行代码”更能反映 Harness 是否真的有效。

## 十、团队怎么落地

最小落地方式很简单。

### Step 1：统一默认入口

日常任务默认：

```text
sdd-riper-one-light
```

复杂任务再切：

```text
sdd-riper-one
```

### Step 2：统一任务输入格式

所有中等以上任务，至少说清：

```text
目标
范围
约束
验证
```

### Step 3：统一执行前检查

代码修改前，必须看到：

```text
Restated Understanding
Core Goal
Done Contract
Checkpoint
Risk
Validation Plan
```

没有这些，就不算进入 Harness。

### Step 4：统一收尾回写

任务结束后，必须留下：

```text
Change Log
Validation Result
Remaining Risk
Resume / Handoff
```

这个回写比“已完成”三个字重要得多。

## 十一、怎么判断它有没有跑起来

不要只看“有没有用了 AI”。

应该看六个证据：

1. 有没有任务真相源：中等以上任务有没有 spec、summary 或 handoff。
2. 有没有执行前设闸：Agent 修改前是否讲清目标、边界、动作、风险、验证方式。
3. 有没有明确批准：是否仍然允许 Agent 不经 checkpoint 直接大改。
4. 有没有外部证据：完成是否由测试、编译、运行、日志、接口返回、截图或人工验收证明。
5. 有没有顺水修正：模型提出不同实现路径时，人是否根据目标、边界、风险和证据判断，而不是只按原设想否定。
6. 有没有经验回写：任务结束后是否留下改了什么、为什么改、风险是什么、下一轮从哪里接。

有这些，AI Coding 才会从个人技巧变成团队资产。

## 十二、常见误区

### 误区一：light 是轻，所以不严谨

轻量不是少控制。

轻量是少低价值文本，保留高价值锚点。

`sdd-riper-one-light` 之所以轻，是因为它相信强模型可以自分解；但它仍然要求目标、边界、证据和恢复点。

### 误区二：用了 Skill 就不用人判断

不是。

Skill 不能替代人的任务切分能力。

最小混沌单元仍然要人来判断。Skill 只是护栏，不是驾驶员。

### 误区三：所有人都必须永远照范式跑

不是。

固化范式是给不太熟的人先建立安全习惯。

真正熟练以后，你可以自由使用，只要不丢掉目标、边界、证据和恢复点。

### 误区四：水流理论就是放任模型

不是。

水流理论不是让模型想干什么就干什么。

它要求边界更清楚，证据更硬，回炉点更明确。

只是它不要求模型按人类预设的每一步走，而是允许模型在边界内选择更自然的路径。

### 误区五：文档越完整越好

不一定。

文档的目标不是完整，而是可恢复、可验证、可决策。

小任务写 micro-spec。

复杂任务写 standard spec。

长任务写 handoff。

任务收敛后 archive。

不要为了文档而文档。

## 十三、最后总结：心法、协作和范式

这篇文章真正想讲的，就是三层。

第一层，是大道至简的 Harness 心法：

> 把任务切成合适大小的最小混沌单元。
> 目标清楚，边界可见，上下文足够，结果能验，失败能局部重来，同时给模型足够自主空间。

第二层，是水流理论：

> 把任务交出去以后，不微操模型的每一步。
> 人维护方向、边界、风险、证据和回炉判断；模型在边界内按更适合代码地形和自身能力结构的方式推进。

第三层，才是给不太会、不太懂、还没有手感的人使用的固化范式：

> 用 `sdd-riper-one-light` 固定少数关键锚点：Spec、Checkpoint、Validation、Reverse Sync、Handoff、Archive。

成熟的人不应该被范式绑住。

但没有范式的人，也不能直接裸奔。

`sdd-riper-one-light` 和 `sdd-riper-one` 的价值，就在这个中间层：

- 它不把 AI Coding 写死。
- 它不替代人的判断。
- 它只把最容易失控的地方，用最小锚点卡住。
- 它让新手先安全跑起来。
- 它让熟手把经验沉淀下来。
- 它让团队从个人手感，慢慢变成组织能力。

这就是我理解的 Light Harness。

不是律令。

不是重流程。

是一套足够轻、足够松，但关键时刻能兜住任务的 AI Coding 护栏。
