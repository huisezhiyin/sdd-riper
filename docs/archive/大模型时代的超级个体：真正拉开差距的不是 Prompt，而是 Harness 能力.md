# 大模型时代的超级个体：真正拉开差距的不是 Prompt，而是 Harness 能力

**大模型时代，真正拉开程序员差距的，不是会不会用 AI，也不是 Prompt 写得多漂亮，而是能不能把一个任务拆成合适大小的子任务，定义好边界和 checkpoint，让模型自主推进，再由人类判断放行、修改还是回炉。**

我越来越觉得，Harness 的核心不是 Prompt，不是长上下文，也不是工具数量。

**Harness 的核心，是控制混沌的尺度。**

大模型不是确定性程序。它更像一个高能力的概率输出器。同样的输入，它可能走对，也可能走偏；可能抓住重点，也可能被噪音带走。

所以 Harness 要解决的，不是“怎么给模型更多东西”，而是怎么把一个混沌系统切成合适大小、边界清楚、反馈及时的小系统。

## 一、一大坨不是 Harness

很多所谓 Harness，其实只是把超长 Prompt、大量上下文、一堆工具都塞给模型，然后让它自己长时间运行。

这不是 Harness。

这只是把混沌包装得更豪华。

问题不在于 token 用得多，而在于上下文熵太高。长上下文不等于高质量上下文。工程任务里，上下文越长，目标越容易被稀释，旧决策和新决策越容易打架，模型越难知道现在真正重要的是什么。

我不关心“省 token”，我更关心“省上下文”。

所谓省上下文，不是少给信息，而是只让模型面对当前子任务真正需要的信息。一个干净的小上下文，往往比一个庞大的杂乱上下文更能释放模型能力。

这也是我自己的强烈体会：在一个点上和大模型讨论太久，反复拉扯太多轮，往往不是越讨论越清楚，而是开始污染上下文。旧方案、废弃前提、临时猜测、已经否掉的路径，全都留在对话里，模型的注意力会被这些残留信息分散。

**拆分子任务和设置 checkpoint 的价值，不只是管理进度，也是主动切断上下文污染。**

一个子任务完成了，就检查、放行或回炉。不要让它拖着一堆历史噪音继续污染后面的任务。

## 二、核心能力：切到合适大小

可以把一次大模型任务理解成一个混沌系统。

任务越大，变量越多，随机偏移越容易累积。但任务也不是越小越好。如果你把任务拆到“写这个函数第一行”“现在写第二行”，那就回到了古法编程。人类 step by step 遥控模型，模型只是打字员。

所以 Harness 的关键，不是大，也不是小，而是合适。

太大，熵太高，模型会漂。太小，自由度太低，人类变成遥控器。刚好，模型能发挥，人类能判断，失败能局部重来。

一个极限例子就能说明这件事。

如果你让大模型实现一个简单的 `add(a, b)` 函数，它大概率可以做得很好。任务空间极小，目标、边界、验证都清楚。

但如果你让它“做一个支持高并发、还能抢红包的直播系统”，即使你给它再长的 Prompt、再多的工具、再大的上下文，它也很难一次稳定做好。

因为这根本不是一个任务。

它里面包含架构、并发、资金安全、风控、消息链路、状态一致性、降级、监控等一组耦合很强的子系统。你把它当作一个任务交给模型，就是把一个巨大混沌系统直接扔进模型里。

问题不是“大模型能不能做”，而是你有没有把它拆成合适大小的 Harness 单元。

**这个“合适大小”，就是大模型时代程序员最稀缺的判断力。**

本来任务拆解就是程序员的基本能力。但大模型时代，这个能力被放大了。以前你拆任务，是为了自己写代码更清楚、团队协作更顺。现在你拆任务，是为了给概率系统设计合适的运行空间。

一个合适的子任务，应该小到目标清晰、边界可见、结果能验、失败能重来；又要大到模型仍然有自主推进空间。

这就是“船小好调头”。一个节点失败了，不可怕，补上下文、换方案、重跑这个节点就行。一大坨任务失败了就很贵，因为你很难判断到底是需求错了、上下文错了、工具错了、计划错了，还是模型中途漂了。

## 三、Checkpoint 和边界

如果子任务是 Harness 的运行空间，那么 checkpoint 就是这个子任务完成后的检查点。

Checkpoint 的价值，不是让模型写计划作文，而是让人类在一个子能力闭环后检查：它完成得怎么样，能不能放行，需不需要修改，还是应该回炉。

还是拿直播系统举例。

这个系统不能作为一个整体丢给模型。但它可以被拆成多个大小适中的子能力：聊天室、禁言、会员展示、高并发消息链路、红包资金安全。

每个子能力都不等于整个直播系统，但每个子能力都应该足够完整，完整到人类能判断它是否闭环。

比如“聊天室”不是整个直播系统，但它可以形成一个闭环：消息能发出去，能被接收，能被展示，失败时有基本反馈。做到这里，人类就能判断这个子能力是放行、修改，还是回炉。

再比如“禁言”也不是整个权限系统，但它也应该能闭环：谁能禁言，禁言后消息是否被拦住，解除后是否恢复。它足够小，不会吞掉整个直播系统；也足够完整，不需要人类逐行遥控。

**Checkpoint 关注的是：这个子能力有没有完成。边界设计关注的是：这个子能力有没有破坏别的能力。**

如果这一轮做的是禁言，边界就不是一句“实现禁言功能”。真正的边界是：它不能破坏聊天本身，不能误伤正常用户，不能侵入会员展示，也不能让消息链路因为禁言判断整体变慢。

如果这一轮做的是会员展示，它就不应该顺手改变聊天发送、权限判断或红包链路。它是展示能力，不是核心协议改造。

所以 Harness 需要反馈面：测试、Review、测试环境验证、日志观察，以及必要时的回滚点。

这些东西不是流程装饰。它们是在回答一个更底层的问题：

**这轮 Harness 有没有把系统炸掉？**

一个子任务本身做完了，不代表它可以被放行。它还必须证明自己没有破坏不该破坏的东西。

## 四、超级个体不是 Prompt 高手

大模型时代的超级个体，不是 Prompt 高手，而是 Harness 驾驶员。

他能把模糊需求拆成适合模型推进的小单元，能定义每个单元的边界和 checkpoint，能让模型在子任务内自主实现，能在 checkpoint 上判断放行、修改还是回炉，最后还能回到全局目标做整体检查。

他的效率高，不是因为他敲代码更快，而是因为他能让模型、任务、边界、文档和反馈面组成一条稳定的交付链路。

相反，不会 Harness 的程序员会越来越危险。

他可能也在用 AI，但只是把大任务扔进混沌系统，然后等待奇迹。

模型越强，这种差距越大。因为强模型会让会驾驶的人更快，也会让不会驾驶的人更快地制造混乱。

管理者也应该意识到这一点。未来识别一个程序员，不能只看他会不会写代码、会不会用 AI 工具，还要看他面对一个真实任务时，能不能拆出合理的子任务，能不能说清边界，能不能知道哪里该 checkpoint，能不能让失败局部重来。

工具会变，模型会变，但任务分解和边界设计不会过时。

## 总结

真正的 Harness，不是一大坨 Prompt，不是更长上下文，也不是更多工具。

它的本质是：把大模型这个混沌系统切成合适大小的子任务，定义每个子任务的边界和 checkpoint，让模型在边界内自主推进，让人在 checkpoint 上判断放行、修改或回炉，最后再回到全局目标做整体检查。

这件事听起来没有某个模型版本、某个插件、某段 Prompt 那么炫。

但它会成为大模型时代程序员最核心的能力之一。

会的人，会变成超级个体；不会的人，会被大模型放大自己的混乱。
