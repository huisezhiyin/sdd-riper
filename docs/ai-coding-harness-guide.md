# 别再把大需求直接丢给模型：一套可复制的 AI Coding Harness 工作法

这篇文章只解决一个问题：怎样把真实工程任务交给 Coding Agent，让它可以自主推进，同时保持可检查、可恢复、可验收。

如果你想先理解背后的判断，读[《Code is cheap. Don't write any.》](./code-is-cheap.md)。这里不再重复理念，直接进入工作法。

## 先调三个旋钮

把任务交给模型前，先检查三个旋钮。

### 任务大小

任务应该足够大，让模型能完成一个有意义的闭环；也要足够小，让人可以判断它到底有没有完成。

“重构权限系统”通常太大。“把权限入口统一到新网关，保留旧入口兼容层，并用现有集成测试证明行为不变”更接近可执行单元。

### 上下文

模型需要的是当前决策必需的地形，不是整个世界。

- 项目规则从 `AGENTS.md` 进入；
- 稳定事实从项目知识或历史 Spec 进入；
- 陌生代码先通过 `codemap` 建索引；
- 日志、截图、需求和讨论记录只提炼与当前任务相关的部分；
- 已否决的方案不要继续留在活跃上下文里制造噪音。

### 自由度

自由度跟反馈速度和破坏面有关。

- 原型、文档、小范围重构：可以让模型自己找路；
- 老系统、跨模块变更：限制修改范围，并设置中途 checkpoint；
- 权限、发布、删除、迁移：明确文件、命令和不可执行动作，关键步骤前等待批准。

## 用任务包代替大 Prompt

任务包不是一篇长设计文档。它只需要让模型和人对同一件事形成契约。

```text
Goal
  最终要发生什么变化。

Context
  先读哪些规则、spec、codemap、代码、日志或需求。

Boundary
  可以改什么，不能改什么；哪些动作需要再次批准。

Done Contract
  什么算完成，由哪些命令、结果或人工检查证明。

Recovery
  如果暂停或失败，状态写到哪里，下一轮从哪里恢复。
```

![任务包把目标、上下文、边界和证据放进同一个闭环](./assets/agent-task-package.png)

任务简单时，这五项可以只有几行；任务复杂时，再把它升级成 Feature Spec。不要为了形式写长文，也不要在目标仍然模糊时直接开工。

## 三种常见起手式

### 陌生老项目

先找地形，不要先改代码：

```text
请使用 codemap 梳理这次功能涉及的入口、调用链、状态、依赖、风险和验证入口。
只建立索引，不要修改代码。
```

拿到 CodeMap 后，再切出本轮最小闭环。CodeMap 的价值不是替代源码，而是告诉模型下一步只需要回读哪一小片源码。

### 从零开始

新项目没有历史包袱，但目标最容易发散。先写清 MVP 和明确不做：

```text
Goal: 一条命令创建 room，让两个参与者给出建议并留下 transcript。
Out: Web UI、云同步、固定角色市场、复杂权限系统。
Done: CLI 演示通过，关键状态有测试，README 给出最小用法。
```

### 简单 Bug

小任务不需要完整阶段流，但也不能裸奔：

```text
Goal: 修复 room show 看不到刚生成 artifact 的问题。
Boundary: 只改 artifact 写入和读取链路，不重构存储层。
Done: 复现用例先失败、修复后通过，相关回归通过。
```

## 一轮任务怎么跑

### 1. 复述

让模型先用自己的话说明目标、边界、风险和验证方式。复述不是礼貌动作，它会提前暴露“看似同意、其实理解不同”。

### 2. 落最小 Spec

把确认过的目标和决策写到聊天外。后续发生转向时更新同一份真相源，不要让新结论只留在对话尾部。

### 3. 执行前 checkpoint

模型在改文件前应给出：

- 准备改哪些文件；
- 为什么是这些文件；
- 最小实现路径；
- 明确不做什么；
- 准备怎样验证。

确认后才执行。低风险文档和纯机械修改可以降低门禁，高风险动作不能省略。

### 4. 自主推进

批准以后，让模型连续完成探索、实现、测试和必要修复。不要把每个函数都变成人工审批点。

当模型到达真正的决策点，人只需要选择：放行、阻止、绕道、回炉、追问或补充上下文。

以下情况应该主动打断：

- 新发现与 Spec 冲突；
- 修改范围开始外溢；
- 连续验证失败但仍沿同一路径重试；
- 准备执行外部写入、发布、迁移或不可逆动作；
- 模型无法用证据解释为什么已经完成。

### 5. 用证据收口

一份可交付的完成报告至少回答：

```text
改了什么？
跑了什么验证？
验证结果是什么？
Done Contract 哪些已经满足？
哪些风险没有覆盖？
README、Spec、AGENTS.md 或示例是否需要同步？
```

测试命令通过并不总是终点。接口行为、日志、截图、监控、灰度和人工验收，应该按任务风险逐层增加。模型说“完成了”不是证据。

### 6. Reverse Sync

把验证过的结论写回正确的位置：

- 当前任务的决策和结果回写 Feature Spec；
- 暂停和交接状态写入 handoff；
- 稳定、跨任务复用的事实，经确认后写入项目知识；
- 用户行为和公开功能变化更新 README 或示例。

## 什么时候换新对话

如果一条对话已经混入大量旧假设、否决方案和重复诊断，不要硬撑。先把当前事实、已完成内容、剩余目标、边界和验证风险写进 Spec / handoff，再使用 [`new-chat-ready`](../skills/new-chat-ready/) 创建精简 resume pack。

新对话只读取恢复任务需要的最小切片。旧对话留作历史，不再让它污染实施上下文。

## 团队落地不需要一篇千行制度

团队第一次采用这套方法时，先统一五条默认规则就够了：

1. 日常任务默认使用 `sdd-riper-one-light`；
2. 陌生代码先建 CodeMap；
3. 代码和高影响动作前必须有 checkpoint；
4. 完成必须给验证证据；
5. 长任务和交接必须留下可恢复状态。

先选一个边界清楚、风险可控的真实需求试跑。复盘时看返工次数、人工介入点、验证缺口和恢复成本，而不是先宣传一个夸张的效率百分比。流程只有在真实任务里减少了失控和返工，才值得扩大。

## 四个 Skill 怎么配合

| Skill | 什么时候用 |
| --- | --- |
| [`sdd-riper-one-light`](../skills/sdd-riper-one-light/) | 日常默认任务，低摩擦推进 |
| [`sdd-riper-one`](../skills/sdd-riper-one/) | 高风险、训练、审计、复杂重构和密集交接 |
| [`codemap`](../skills/codemap/) | 陌生代码、大模块、遗留系统和跨仓任务 |
| [`new-chat-ready`](../skills/new-chat-ready/) | 新对话、长暂停、handoff 和上下文恢复 |

最后只记住一句话：**不要把大需求直接丢给模型；把一个有地形、有边界、有证据出口的任务包交给它。**
